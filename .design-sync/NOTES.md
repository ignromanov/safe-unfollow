# design-sync notes — safe-unfollow

Repo-specific gotchas for future syncs. Read this before re-running the converter.

## ⛔ NEVER reconcile-delete in this project — 52 files are hand-authored

The target project (`5e633d36-642a-4605-8000-3ecc1eecb00c`) **pre-dates design-sync** and was
adopted, not created by it. Alongside the converter's output it holds a hand-authored design
system that the converter does not produce and therefore cannot re-create:

| Path                           | Count | What                                                                                                 |
| ------------------------------ | ----- | ---------------------------------------------------------------------------------------------------- |
| `foundations/*.card.html`      | 18    | Colour, type, spacing, radius, shadow, motion, brand, icon specimens                                 |

The upload section's reconciliation-delete step assumes _everything in the project came from
this sync_ — true for a freshly created project, **false here**. Following it literally deletes
all 41. Decided 2026-08-09 by the owner: **`deletes: []`, always**, until the day a synced
component is genuinely renamed or regrouped — and even then, delete only that component's own
stale paths, enumerated by hand.

Coexistence is by design, not by accident: `DESIGN-GUIDE.md` opens with _"Companion to
`README.md` (which is generated by the code sync)"_ — its author knew the converter owns
`README.md` and put the judgment in a separate file. The hand-authored cards use the same
`<!-- @dsCard group="…" -->` mechanism as synced ones, so both register in the DS pane.

⚠ **One shared surface is a real coupling**: `foundations/*.card.html` `<link>`s `../styles.css`
and reads `--background` / `--foreground` / `--border` / `--muted-foreground`. The converter
overwrites `styles.css` on every upload. It currently works — verified 2026-08-09, all four
tokens defined twice (light + dark) in the `_ds_bundle.css` closure, Inter shipped — because
both sides derive from the same Tailwind config. **A `cssEntry` change would silently unstyle
18 hand-authored cards, and no converter check would catch it.**

**The count above was 41 until 2026-08-20, and the undercount was the dangerous kind: it named
four root text files where there are six, and omitted `handoff/` and `templates/` entirely.**
A guard rule that enumerates what it protects is only as good as the enumeration — `SYNC-ADVICE.md`,
both handoff documents and the mockups' own loader were outside it. Re-derive this table from
`DesignSync list_files` rather than trusting it; the converter's output is everything NOT listed
here (`components/` `_preview/` `_vendor/` `fonts/` `guidelines/` `styles.css` `README.md`
`_ds_bundle.*` `_ds_manifest.json` `_ds_sync.json`), which is the cheaper half to identify.

Backup: `designs/claude-design-project/` in the repo — **43 of the 52 now, up from 1.** Until
2026-08-20 only `DESIGN-GUIDE.md` was copied, on the reasoning that nothing was being deleted;
that reasoning protects against reconciliation and against nothing else, while the guard rule
itself lived in this file, which had just been lost with the worktree. Deliberately not copied:
the 8 `assets/` (verified 2026-08-20 — all eight have local sources in `public/` and
`designs/screenshots/`) and `.thumbnail`.

One correction worth keeping: `templates/conversion-audit/support.js` is 69 KB of **Claude Design's

and was nearly skipped on that basis — but it is the parser for `<x-dc>`, so without it the four
backed-up `.dc.html` mockups are inert files. It is vendored deliberately; do not "clean it up".

## The `--remote` anchor is already on disk — check before fetching it

`resync.mjs --remote` wants the project's `_ds_sync.json`, and the skill text says to fetch it
with `DesignSync get_file`. In practice the last successful upload left a byte-identical copy at
`ds-bundle/_ds_sync.json`, since that is the file the previous run emitted and uploaded. Compare
`bundleSha12` and `auxSha` against the remote before trusting it — if they match, it _is_ the
anchor, and copying it aside costs nothing while transcribing ~300 hashes through the model
costs thousands of tokens and can corrupt one.

Copy it aside **before** running the build: `package-build` rewrites `ds-bundle/` in place.

`.design-sync/.cache/baseline-sync.json` is **not** a substitute — on 2026-08-12 it held 95
components against the project's 99, with three of four shas different. It predates the last
upload rather than recording it.

## This repo is an app, not a published component library

`package.json` is `private: true` with no `main` / `module` / `exports`, and
`npm run build` produces an SSG **site** (`vite-react-ssg build`), not a component
`dist/`. The converter therefore runs in **synth-entry mode**: it synthesizes an
entry from `src/` and the emitted `.d.ts` prop contracts are weaker than a real
build would give. This is expected here, not a fault to chase.

## Two setup steps that are NOT in the repo and must be redone on a fresh clone

**As of 2026-08-20, `bash .design-sync/tools/preflight.sh` runs both steps below in one
command** — plus staging the skill's converter, installing its deps, and emitting the
`.d.ts` declarations ("`.d.ts` extraction" further down). The script automates the steps;
it doesn't change what they do or why skipping them fails the way described here, so the
detail below is still worth reading once.

1. **Self-link the package into node_modules:**

   ```sh
   ln -sfn .. node_modules/safe-unfollow
   ```

   The converter resolves the DS at `<node_modules>/<pkg>` (`package-build.mjs`
   `PKG_DIR = join(NODE_MODULES, PKG)`). In the package's own repo that path does
   not exist, and the failure is an unhandled `ENOENT` from `dts.mjs:87`, not a
   tagged diagnostic. Symptom to recognise: the first log line reads
   `safe-unfollow@0.0.0` instead of the real version — the converter fell back to
   `{ name: PKG }` because it never found the manifest.

2. **Compile the stylesheet** (see next section):
   ```sh
   node .design-sync/tools/compile-css.mjs
   ```

## cssEntry must be COMPILED Tailwind v4, never `src/styles.css`

`src/styles.css` is a Tailwind v4 **source** file (`@import 'tailwindcss'`).
esbuild cannot resolve it — Tailwind v4 exposes `.` only under the `style` export
condition, so bundling dies with `Could not resolve "tailwindcss"` and
`"tw-animate-css"`.

`.design-sync/tools/compile-css.mjs` compiles it through the repo's own `@tailwindcss/postcss`
into `.design-sync/.cache/app-compiled.css`, which `cfg.cssEntry` points at.

**Do not point `cssEntry` at `dist/assets/app-*.css`.** It works, but the filename is
content-hashed and moves on every app build, so it is a terrible re-sync anchor. The
compiled path above is stable and reproducible.

The wrapper at `.design-sync/tools/ds-tailwind.css` adds `@source "../previews"` so
utility classes used _only_ by authored preview `.tsx` files still get generated.
**If an authored preview renders unstyled, check this first** — a class no app source
file uses will not exist in the compiled CSS otherwise.

⚠ **Re-run `compile-css.mjs` after every source change, not once per session.** The
failure it prevents does not look like a failure. On 2026-08-12 a paywall fix added
`pe-6` — the first use of that utility anywhere in the app — with the stylesheet compiled
before the edit. Everything downstream was green: the class was in `_ds_bundle.js`,
`package-validate` reported 98/99 clean, and the contact sheet rendered a component that
looked exactly like the one before the fix, because the rule did not exist to apply. Four
other new utilities in the same commit (`font-display`, `text-5xl`, `min-h-11`,
`shadow-primary/30`) were already used elsewhere and compiled fine, so only the novel one
went silently inert.

The check is one line, and it is on the CSS rather than on the render:

```sh
grep -c '<the-new-class>' .design-sync/.cache/app-compiled.css   # 0 means inert
```

Production is unaffected either way — the app's own Tailwind pass scans `src/` at build
time. The divergence lives only in the design system, which makes it worse, not better:
the design agent would be building against a component that behaves differently from the
shipped one.

Verified after compiling: 22 `@font-face` rules harvested, 11 `url()`s rewritten into
`fonts/`, 284 OKLCH token references, and Tailwind rewrites font urls to correctly
resolving relative paths (`../../node_modules/@fontsource-variable/...`).

## srcDir is narrowed to `src/components`

With `srcDir: "src"` the synth entry swept in `src/main.tsx`, whose line 5 is
`import './styles.css'` — which is what dragged the unbuildable Tailwind source into
the JS bundle. It also pulled in `src/__tests__/test-utils.tsx`. The converter's own
filter only excludes `.test.` / `.spec.` / `.stories.` files, so neither was caught.

`srcDir: "src/components"` fixes the import chain and scopes discovery to the actual
component surface. Consequence to be aware of: components under `src/pages/` are
deliberately **out of scope** — they are route pages, not design-system components.

## Render check: use the installed Chrome, do NOT download a browser

The `~200MB npx playwright install chromium` step is unnecessary.

```sh
DS_CHROMIUM_PATH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  node .ds-sync/package-validate.mjs ./ds-bundle
```

- `npm i playwright` inside `.ds-sync/` pulls **~18 MB of JS only** — the postinstall
  browser hook was removed from the npm package around v1.39.
- The harness hardcodes `pw.chromium.launch()` and does not support Playwright's
  preferred `channel: 'chrome'`, but it honours the `DS_CHROMIUM_PATH` env var as
  `executablePath` (`package-validate.mjs:439`, `package-capture.mjs:100`).
- **Version compat is the thing to re-check**, since `executablePath` bypasses
  Playwright's own compatibility guard. Verified working 2026-08-08: Playwright
  1.62.1 (bundles Chromium 151) against Google Chrome 151.0.7922.77 — exact major
  match. If Chrome auto-updates well past the installed Playwright, either bump
  Playwright or fall back to `npx playwright install chromium`.

## `.d.ts` extraction needs BOTH a declaration emit and the `dts.mjs` fork

Out of the box **all 95 components shipped an empty contract** (`[key: string]: unknown`),
which is the single worst failure mode here: the design agent would know `Button` exists
but not that it takes `variant` or `size`. Two independent causes, both needed fixing:

1. **No declarations exist.** The repo ships no `.d.ts`. Emit them before every sync:

   ```sh
   npx tsc -p .design-sync/tools/tsconfig.dts.json    # → dist/types/, 136 files
   ```

   `findTypesRoot` probes `dist/types` before falling back, so this is picked up with
   **no `package.json` change**. tsc reports errors (`types: []` drops `vite/client`, so
   `import.meta.env` is untyped) but **emits anyway** — that is expected, not a failure.
   `dist/` is gitignored, so this costs the repo nothing.
   → this alone took contracts from 0/95 to 32/95.

2. **`propsBodyFor`'s fallback was unreachable.** It looks up `<Name>Props` first, then
   falls back to the component's first call signature — but the fallback reads
   `project.getSourceFile(entry)` where `entry` is `<pkgDir>/index.d.ts`. An app has no
   barrel, so that is _always_ undefined and the fallback returned null before it started.
   The 32 that worked were exactly the components whose source declares an explicit
   `Props` interface (`rules/code-style.md` mandates it); every shadcn/ui primitive
   declares props inline via `forwardRef<ElementRef<typeof X>, ComponentPropsWithoutRef<typeof X>>`
   and therefore had none.
   `.design-sync/overrides/dts.mjs` makes the fallback scan the package's own `.d.ts`
   files for the export instead. → 32/95 to **85/95**.

The remaining 10 (`PageLoader`, `Footer`, `SkeletonItem`, `LanguageSwitcher`,
`BreadcrumbSchema`, `OrganizationSchema`, `FAQSection`, `FilterChipsSkeleton`,
`RouteErrorPage`, `UploadAffiliateBlock`) genuinely take **no props** — verified against
`dist/types` (`export declare function PageLoader(): JSX.Element`). An empty contract is
honest there; do not "fix" it.

## Authoring previews

- Import from `'safe-unfollow'` — esbuild externalises it to `window.SafeUnfollow`. **Your
  editor will show `Cannot find module 'safe-unfollow'` on every preview file.** Expected
  and harmless; the package has no `exports` map, and the import never resolves at type time.
- **Run `node .design-sync/tools/compile-css.mjs` before rebuilding whenever previews use new utility
  classes.** The wrapper's `@source "../previews"` scans authored previews, but the compile
  is a separate step. A class no app source uses will not exist otherwise, and the preview
  renders unstyled while looking like a component bug.
- Because parallel authoring agents **cannot** recompile that shared stylesheet, the wrapper
  carries an `@source inline(...)` safelist of the common layout vocabulary. Extend it there
  rather than telling agents to avoid classes.
- Radix compounds work; use `defaultValue`/`defaultOpen`/`open` for statically-open states.
  lucide icons bundle correctly.

## One preview file per EXPORT — compound parts do not inherit the parent's

The converter resolves `.design-sync/previews/<Name>.tsx` by exact component name. A file
covering several exports (e.g. an `Alert.tsx` that also uses `AlertTitle` and
`AlertDescription`) gives previews to **`Alert` only** — the other names fall through to the
floor card. `preview-rebuild.mjs` prints `no <Name>.tsx … skipped` for them, which reads like
an expected message and is easy to rationalise away; it is actually the sound of five
components losing their cards.

Caught during wave 1: an agent authored `Alert.tsx` + `Tabs.tsx` and reported "12/12 good",
but `AlertTitle`, `AlertDescription`, `TabsList`, `TabsTrigger`, `TabsContent` had no preview
and **no grade file**. The proof is in the artifact, not the report: an authored card's
`.html` contains `dsPreview` references (3 for `Alert.html`), a floor card contains **0**
(`AlertTitle.html`). The same agent got it right for Accordion — separate `AccordionItem.tsx`,
`AccordionTrigger.tsx`, `AccordionContent.tsx`, each a full working composition.

**Rule**: every compound part gets its OWN file, containing a full working parent composition
with content distinct from its siblings (otherwise four cards screenshot the same thing).

## Component facts worth knowing before authoring

- **`AlertTitle` has `line-clamp-1`** — single-line by design; a long title truncates with an
  ellipsis rather than wrapping. Put detail in `AlertDescription`, which does wrap.
- **`AccordionTrigger` has no `disabled:` variant at all.** Radix sets `data-disabled` and
  nothing styles it, so a "disabled" cell screenshots identically to the default and fails the
  rubric's _variant axis actually varies_ check while being technically correct. `TabsTrigger`
  **does** carry `disabled:opacity-50`, so the same cell idea works there. Check the source
  `className` for a matching state variant before blaming a preview.
- **`lucide-react` imports and renders fine inside preview files** — resolved from
  `node_modules` like any other dep, no bundler config needed.
- ⚠ **`Alert`/`AlertTitle`/`AlertDescription` — this bullet's original claim expired
  2026-08-17.** It read: "no real usage anywhere in `src/` ... every 'Alert' grep hit is
  `AlertDialog` or the lucide `AlertTriangle` icon", so the existing `Alert.tsx` preview was
  built from locale copy strings, not ported usage. GH#41 shipped `FollowRequestsCaveat`, a
  real `Alert` consumer (see the 2026-08-17 section below) — the existing preview is still
  fine, but a future pass could re-derive it from that real composition instead.
- ⚠ **The `Dialog` consumers NOW EXIST — this bullet's original claim expired on 2026-08-09.**
  It read: _"`PaywallModal`, `ExportDialog`, `LicenseDialog` live on the unmerged
  `feat/pro-export` branch"_. PR #11 merged as `8d18523`, so all three (plus
  `ResultsExportControls`) are real exports in `main` with real `.d.ts` contracts. The wave-1
  `Dialog*` previews were composed from `architecture/components.md` prose against components
  that did not exist; **they should now be re-derived from the shipped source**, which is both
  ported usage and a stronger composition. Treat any surviving prose-derived cell as a
  to-do, not as evidence.

## `cfg.overrides.<Name>.skip` is inert in this shape — do not reach for it

Cost a crashed build on 2026-08-09. Three separate facts, each enough on its own:

1. **`skip` is an array of story ids, never a boolean.** `emit.mjs:368` does
   `new Set(OVERRIDES[c.name]?.skip ?? [])`, so `{"AdSlot": {"skip": true}}` dies with
   `TypeError: boolean true is not iterable` — after the converter has already wiped
   `--out`. A crashed build leaves no bundle at all, so preserve anything you need from
   `ds-bundle/` (notably `_ds_sync.json`) **before** running one.
2. **The story ids it filters only exist in the storybook shape.** `c.storyIds` is
   populated in `source-storybook.mjs` / `preview-gen-storybook.mjs`; this repo is
   `shape: package`, where the field is never set.
3. **It cannot touch an authored preview.** `package-build.mjs:801` passes `skip` into
   `generatePreviewSource`, i.e. the _generated_ tier only. With 61 user-owned previews
   the build logs `previews: 0 generated`, and `skip` never runs.

**Therefore**: a component with no `.design-sync/previews/<Name>.tsx` already falls to the
floor card — `AdSlot` and `BuyMeCoffeeWidget` need no config at all, and the floor card is
the documented honest baseline, not a failure. A component _with_ an authored preview can
only be suppressed by removing that file. The prior note below said both "want
`cfg.overrides.<Name>.skip`"; that was written from the skill's prose, never executed.

## Three components cannot be previewed at all (skip, don't fight)

Do NOT spend another wave on these. No preview file → honest floor card. That is the outcome.

- **`AdSlot`** returns `null` before any markup unless `import.meta.env.VITE_ADSENSE_CLIENT`
  is set, _in addition_ to a non-empty `slot` prop (`src/components/ads/AdSlot.tsx:90`). No
  `cfg.*` field injects an env define (verified against every `cfg.` reference in
  `package-build.mjs` and `preview-rebuild.mjs`), so even the reserved layout box is
  unreachable. (The old advice here — "wants `cfg.overrides.AdSlot.skip`" — is wrong; see the
  section above.)
- **`BuyMeCoffeeWidget`** also returns `null`. Its entire visible effect is injecting a
  `<script>` into `document.head` and later a floating button into `document.body` — both
  outside its own mounted container, so no screenshot of the component's box can ever show it.
- ⚠ **`ResultsExportControls`** — added 2026-08-09, found by the wave-2 `export` batch and
  verified independently. Early-returns `null` at `ResultsExportControls.tsx:81` unless
  `isExportFeatureEnabled()`, which chains through `getApiBase()` to
  `import.meta.env.VITE_DODO_CHECKOUT_URL`. The gate can never open in a preview build:
  `.ds-sync/lib/common.mjs:141` hardcodes the esbuild define as the literal
  `{"MODE":"development","DEV":true,"PROD":false,"SSR":false,"BASE_URL":"/"}` — a **full
  replacement** of the `import.meta.env` expression carrying no `VITE_*` keys at all, so the
  property is `undefined` in every preview regardless of the shell environment at capture time.
  Note the asymmetry with `AdSlot`: that gate is at least prop-shaped, this one is a single
  all-or-nothing boolean with no partial-credit path.

## Tall full-bleed sections need `viewport`, not `cardMode`

Found by the wave-2 `chrome` batch, verified independently 2026-08-09. `Hero` (`py-12 md:py-32`)
and `FooterCTA` (`py-32 md:py-48`) render correctly but are **vertically** cropped by the
capture's default `900x700`: Hero's trust-badge row and all four feature cards are absent from
the PNG entirely, not merely clipped at the edge.

`viewport` is an **independent** override field, not a companion to `cardMode` —
`preview-rebuild.mjs:194` and `emit.mjs:488` both read `ov.viewport ? { viewport: ov.viewport } : {}`
on the no-`cardMode` branch. `cardMode: "column"` is a width/grid knob and would not have touched
vertical clipping. Applied: `Hero` → `900x1400`, `FooterCTA` → `900x900`.

⚠ Unlike `cardMode`/`primaryStory`, an explicit `viewport` **is** part of the grade key
(`emit.mjs:474`) — adding one invalidates that component's grades. Correct here, but it means a
viewport tweak is never a free presentation-only edit.

Counter-example worth keeping: `Header` is equally full-width and does **not** hit this — its
content is one ~90px toolbar row. The risk is tall multi-section content, not full width.

## `LanguageSwitcher` cannot be forced open from outside

Unlike `DropdownMenu` itself (controllable via `open`/`defaultOpen` + `forceMount`, see below),
`LanguageSwitcher` owns its `DropdownMenu` internally and forwards no open-state prop. The closed
trigger is the only state a preview can legitimately capture — the option list belongs to
`DropdownMenuContent`/`DropdownMenuItem`'s own previews. Not a miss; do not re-investigate.

⚠ **Deleting a preview `.tsx` does not prune its compiled output.** `preview-rebuild.mjs`
prints `no <Name>.tsx … skipped` but leaves the previous `ds-bundle/_preview/<Name>.js` in
place, and `package-capture.mjs` will happily re-screenshot that stale build. Neither script
has a `--clean`/prune flag. If `overrides.<Name>.skip` does not suppress it, `rm` the stale
`_preview/*.js` before the next full `package-build`.

## Capture timing: components that reveal on a timer are invisible

`LoadingTips` fades its cards in at 800 ms / 1100 ms via `setTimeout`
(`src/config/loading-tips.ts`), with no prop to force a revealed state. `package-capture.mjs`
screenshots as soon as Playwright's `waitUntil: 'networkidle'` resolves — well under 800 ms
with nothing else in flight — so the cell is captured in its guaranteed-all-hidden first frame
**every time**. There is no settle-delay or per-cell wait hint in the capture script today.
This is independent of the i18n provider: fixing i18n will not make this component visible.

## `defaultOpen` does not visually open a Radix submenu

`DropdownMenuSub` with `defaultOpen` mounts without the submenu content appearing anywhere in
the viewport, affecting `DropdownMenuSub`, `DropdownMenuSubContent`, `DropdownMenuSubTrigger`
and `DropdownMenuPortal`. It throws no JS error and leaves no empty cell, so
`package-capture.mjs` cannot fail on it — it would have graded `good` silently if the agent
had not read the sheets. A reminder that the render check proves "something painted", never
"the right thing painted".

**The working form** is controlled `<DropdownMenuSub open>` (matching the root
`DropdownMenu`'s pattern) **plus `forceMount` on `DropdownMenuSubContent`**. With that, all
four render the submenu correctly offset, with the sub-trigger's focused background visible.

## `DropdownMenuPortal` has exactly one non-redundant use

In this repo's shadcn wrapper, `DropdownMenuContent` **self-portals internally** but
`DropdownMenuSubContent` **does not**. So wrapping `Content` in `DropdownMenuPortal` is a
no-op, and the component's only meaningful use in this API is wrapping `SubContent`. Worth
carrying into the conventions header — the design agent will otherwise wrap the wrong one.

## Wave-2 findings (2026-08-09) — four harness limits a preview author cannot fix

**1. Long in-flow content is cropped by the 900x700 capture, same as the tall full-bleed pattern.**
Not full-bleed at all — ordinary prose/list sections simply longer than 700px. Heights measured at
900px width via `document.body.scrollHeight`, with a **700px** probe viewport: a 4000px probe gives
false numbers for anything using `min-h-dvh`, because that resolves to the probe height rather than
the content height. Applied: `FAQSection` 900x3050 · `HowToSection` 900x6900 · `PrivacyPolicy`
900x5400 · `TermsOfService` 900x4150 · `ErrorBoundary` 900x950 · `UploadZone` 900x1600.

**2. `Wizard` captures pure white — collapsed, not cropped, and no viewport fixes it.**
`PARKED as previews/Wizard.tsx.blocked`. The capture drives `?story=<Export>` single-story mode,
which wraps the story in `.ds-single`, and `.ds-single{transform:translateZ(0)}` (shared card CSS
in `emit.mjs`) deliberately makes that wrapper the containing block for `position:fixed`
descendants — the trick that keeps portals and overlays inside their card. `Wizard` is
`fixed inset-0` by design, so it sizes against that box; a fixed child never contributes to its
ancestor's intrinsic height, the box collapses toward zero, and the wizard has nothing to fill.
The fix is harness-level (a min-height on `.ds-single`, or exempting stories that need real fixed
positioning). Do **not** try a taller viewport, and do not fake a wrapper height in the preview —
that would misrepresent the shipped component's actual layout.

**2a. What to sync instead, and why this cost real work (2026-08-19).** The parking above is
correct and stays. Its consequence was not recorded and should have been: with `Wizard` absent,
the Claude Design project has **no representation of the guide at all**, so the conversion-redesign
mockup for it (`templates/conversion-audit/FunnelEntry.dc.html` §1B, now copied to
`designs/claude-design-project/`) was drawn as a bare 390px card — no stepper, no close control, no
bottom nav. It was then confirmed as "replace the content of /wizard step 1" in prose. The screen
was designed for one frame and shipped inside another; see the commit that added those mockups.

Do **not** attempt `cardMode: "single"` as a workaround — `.ds-single` **is** the single-story
wrapper whose `translateZ(0)` causes the collapse, so that mode is the failure, not the fix. And
`emit.mjs` may not be forked (`storybook/SKILL.md:259`: app-contract surface). Two real routes:

1. **Upstream**: the harness fix named above — a `min-height` on `.ds-single`, or an opt-out for

### A freshness trap in the capture bookkeeping

A preview edited **after** its capture still matches the grade-key bookkeeping if nothing

## Compound-part previews: byte-identical cards are the failure, and hashing is the check

The wave-2 `AlertDialog` family shipped eleven previews that were **copies of one file** with
different export names. All twenty cells collapsed into exactly **two** distinct images —
`md5` on `_screenshots/review/raw/*.png` proved it in one command. Each card passed the rubric
_individually_ (styled, complete, plausible); the defect exists only **between** components, which
is precisely why a per-component grader cannot see it.

**Use the hash, not the eye.** After any compound-family rebuild:

```sh
find ds-bundle/_screenshots/review/raw -name '*<Family>*' | while read f; do
  printf '%s %s\n' "$(md5 -q "$f")" "$(basename "$f")"; done | sort | uniq -w32 -D
```

⚠ Prune stale cells first. Renaming an export leaves its old PNG on disk, and those stale files
show up as duplicates of each other — the same non-pruning behaviour documented above for
`_preview/*.js`, applied to screenshots.

The remedy is to give each part the axis **it** controls: title length for `AlertDialogTitle`, body
length for `Description`, icon-vs-none for `Header`, button count for `Footer`, panel density for
`Content`, a **closed** dialog for `Trigger` (an open one covers the very element the card exists to
show), a dimmed real page for `Overlay`, a clipping ancestor for `Portal`.

⚠ `AlertDialogTrigger` also needed `viewport: 900x260` and lost its `cardMode: "single"`: with the
dialog closed it can no longer escape its cell, and `single` would have hidden one of its two
variants. A bare button in a 700px-tall card reads as a broken preview — give triggers the toolbar
row they actually ship in.

- ~~**The app requests font families it never declares**~~ — **not since PR #105
  (`d4e5416`, 2026-08-20), and the consequence here was the opposite of what this bullet
  predicted.** It said a fixed app would make `compile-css.mjs` emit 0 aliases, and that the

### Two warnings that must NOT be "fixed"

- **`[RENDER_ERRORS] ErrorBoundary` — false positive by construction.** The preview throws
  `Simulated render error for preview` on purpose; the caught-error fallback _is_ the only
  story this component has (its own box renders nothing when there is no error). Four
  console errors are the expected output. Silencing them would empty the card.
- **`[OVERRIDE_UNDECLARED] dts.mjs is forked but not in cfg.libOverrides`** — emitted
  **before** argument validation. It appears whenever `package-build.mjs` is run without
  `--config`, because the script has not read the config yet and so sees no declaration.
  The entry has been in `cfg.libOverrides` the whole time. Required invocation:
  `node .ds-sync/package-build.mjs --config .design-sync/config.json --node-modules ./node_modules --out ./ds-bundle`

### ThemeProvider: previewable, but not the obvious way

`[RENDER_THIN] … rendered height is 0px` was accurate — `ThemeProvider` is a pass-through to
`next-themes` that emits no wrapper element, so previewing the component alone measures
nothing. It is **not** a fourth member of the un-previewable set (`AdSlot`,
`BuyMeCoffeeWidget`, `ResultsExportControls`): what it delivers is the token palette, and
that is showable.

⚠️ **Side-by-side light/dark is impossible here.** `next-themes` writes the theme onto
`<html>`, not onto the provider's own subtree, so two nested providers with different
`forcedTheme` values still paint one theme. Any preview promising a light/dark pair would be
lying about what the component does. `previews/ThemeProvider.tsx` therefore shows one
palette and says so in a comment.

### Known-dangling, not worth a fork

`ThemeProvider.d.ts` references `Attribute[]`, `ValueObject` and `ScriptProps` — types owned
by `next-themes` and not re-emitted into the contract. It parses cleanly (validate confirms)
and the design agent still gets every prop name and doc string, so the cost of chasing them
through another `dts.mjs` fork is not worth paying.

## Grading findings (2026-08-09, wave 2 close-out)

### `viewport` height is a width control — raising it shrinks the card

The review sheet fits each capture into its row **by height**. A `900x3050` capture in a
~510px row scales by ~0.17, so the story lands at ~150px wide with unreadable type. Every
tall `viewport` override added earlier to stop cropping was therefore trading a crop for a
crush, and on `HowToSection` (`900x6900`) it clipped anyway at step 3 of 9 — the height can
never win that race.

**The right lever for cropping is `cardMode`, not `viewport`.** `column` gives each story
full card width; `single` exempts portal/fixed stories from the grid entirely. `viewport`
should only be used where the aspect stays near-square — kept for `AlertDialogTrigger`
(900x260), `ErrorBoundary` (900x950) and `FooterCTA` (900x900), which all render legibly;
dropped from `Hero`, `UploadZone`, `FAQSection`, `HowToSection`, `PrivacyPolicy`,
`TermsOfService`.

### ⛔ Never set `import.meta.env.DEV` to false

`.ds-sync/lib/common.mjs:141` hardcodes `DEV: true` for the IIFE build, and the visible cost
is real: `DevErrorSelector` renders a dev panel over `UploadZone`'s cards, and
`ErrorBoundary` shows its stack-trace block. The obvious fix is a trap. **The same flag
suppresses analytics delivery** — `lib/stats/core.ts:46,67` and `lib/stats/queue.ts:34` all
early-return when `DEV` is true. Flipping it would make every design rendered on claude.ai
fire real events at our Umami endpoint from a third-party origin. A dev panel in a preview
card is the cheaper failure by a wide margin, and it stays.

### `public/` assets are not in the bundle — two components render broken

Nothing under the app's `public/` dir ships with the sync, so absolute asset paths 404 both
in preview cards and in any design the agent builds:

| Component                             | Asset                                                           | Symptom                  |
| ------------------------------------- | --------------------------------------------------------------- | ------------------------ |
| `UploadAffiliateBlock` / `UploadZone` | `/affiliate/nordvpn-v3-1200x628.webp`                           | broken-image placeholder |
| `HowToSection`                        | `/wizard/step-{1..9}` + suffix (built at `HowToSection.tsx:68`) | nine empty media boxes   |

⚠️ **A literal grep of the bundle under-reports this.** `grep -oE '"/[^"]+\.(webp|mp4|…)"'`
finds only the two affiliate creatives, because HowTo composes its URLs from a base string
at runtime. Count components that _render_ an empty box, not string literals.

### `.render-check.json` already computes the duplicate oracle

The `variantsIdentical` flag per component is exactly the byte-identical-cards check that
was done by hand with `md5` over per-cell PNGs earlier in this session — and it runs over all
99 components, not one family. Read it from the JSON instead of re-deriving it.

### A preview can name a key path that has never existed

`previews/RescueToolCard.tsx` passed `descKey: 'rescue.desc.<tool>'`; the locales have no
`rescue.desc` branch at all — the descriptions live at `rescue.tools.<tool>`. i18next's
default fallback is the key itself, so the card rendered a literal `rescue.desc.publer` and
every other string on it translated correctly, which is exactly what makes this class hard to
spot. Fixed to `rescue.tools.*`. When a preview supplies key names as props, they are not
type-checked against the locale files by anything.

## 2026-08-20: worktree removal deleted three hand-authored files nothing else tracked

`.worktrees/design-sync` (branch `chore/design-sync-main`, merged into `main` as `eaacd1f`
via PR #85) was removed as routine cleanup for a fully-merged branch. `git worktree remove`
gave no warning, because it has none to give: `.ds-sync/`, `ds-bundle/` and
`.design-sync/.cache/` are all gitignored (see "Re-sync risks" above), so nothing under them
was ever staged, backed up, or captured in a skill version. Three files there were
hand-authored and existed nowhere else:

- `.ds-sync/compile-css.mjs` — the Tailwind v4 compiler wrapper ("cssEntry must be COMPILED
  Tailwind v4" above)
- `.design-sync/.cache/ds-tailwind.css` — the `@source "../previews"` wrapper stylesheet,
  same section
- `.design-sync/.cache/tsconfig.dts.json` — the declaration-emit config ("`.d.ts`
  extraction" above)

**The worktree was the trigger, not the mechanism.** `git clean -fdx` — which this file
already names as a hazard elsewhere — would have destroyed the same three files identically,
worktree or no worktree. The actual cause was hand-authored input living under a path this
repo's own `.gitignore` already calls disposable. Reconstruction is happening from this
file's own prose: the sections cited above documented what each file does and why in enough
detail to rebuild them — the only reason this is a recovery and not a rewrite of the compile
logic from scratch.

**Operator-approved fix, 2026-08-20:**

- The three files, plus a new `preflight.sh`, now live in the **committed**
  `.design-sync/tools/` directory. Every path in this file that pointed at
  `.ds-sync/compile-css.mjs` or the two `.cache/` files has been updated to
  `.design-sync/tools/`. `.design-sync/.cache/` keeps only what a script regenerates —
  `app-compiled.css` — and `config.json`'s `cssEntry` still points there unchanged.
  (`fonts-alias.css` was the second such file until 2026-08-21; it is gone with the alias
  step, see the font bullet above.)
- `bash .design-sync/tools/preflight.sh` now runs, as one command, what this file previously
  only documented in prose: stage the skill's converter, install its deps, recreate the
  `node_modules` symlink, compile the CSS, emit the `.d.ts` declarations.
- design-sync no longer runs from a worktree at all (see the correction above); the branch
  it was for is deleted, fully merged.

**The invariant that should outlast these specific files**: a gitignored directory is not
storage, it is a place git has been told not to protect. Anything that costs real time to
reconstruct — as opposed to a re-run of a committed script — does not belong under
`.ds-sync/`, `ds-bundle/`, or `.design-sync/.cache/`, however convenient that location felt
mid-session.
